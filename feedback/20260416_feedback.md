## What went wrong

### Fast-track agent couldn't write files
The fast-track agent hit Edit/Write permission denials and produced a detailed analysis but zero code changes. The orchestrator had to apply the fix manually. **Root cause:** agent tool permissions aren't inherited — each spawned agent needs its own permission grants. This is a platform limitation, not a pipeline design flaw, but the pipeline should handle it gracefully (e.g., the orchestrator should detect the failure pattern and apply changes itself without re-doing the analysis).

### Finalization was skipped
The pipeline defines a clear finalization step (absol-finalizer skill updates state.md, clears todo-run.md, marks tasks done in todo.md). This was never invoked — the orchestrator manually updated state.md and skipped todo.md status updates entirely. **Impact:** todo.md still shows TSK-10–24 as `status: pending` even though they're all done. todo-run.md was never compacted. The pipeline's own state is now inconsistent.

### todo.md task statuses are stale
Executors are explicitly forbidden from modifying todo.md (correct — separation of concerns). But nobody else updated the statuses either. The finalizer is supposed to do this, but it wasn't run. Even if it had been, the current design requires reading todo-run.md job statuses and back-propagating to todo.md — this round-trip is fragile. **Suggestion:** either the orchestrator should update todo.md after each successful executor, or the finalizer must be mandatory (not skippable).

### Planner line numbers go stale immediately
The planner referenced specific line numbers (e.g., "App.tsx line 151", "line 121–124", "lines 77–83"). These were accurate at planning time but wrong by TSK-10's execution. Every executor had to ignore line numbers and search for actual code locations. The planner guidance to executors even said "find actual current locations, ignore stale line numbers" — which means we already know this is a problem. **Suggestion:** planner should reference code by content pattern (function names, variable names, string literals) not by line number. Or accept that line numbers are hints only and stop including them.

### TSK-14 was nearly a no-op
TSK-14 (clean up isDoubleTap from useTapGesture + App.tsx) assumed App.tsx still had isDoubleTap references. But TSK-12 had already removed them all as part of its own scope. TSK-14 only had to clean useTapGesture.ts — a 30-second edit that cost a full agent spawn. **Root cause:** the planner decomposed tasks based on pre-execution state. As tasks execute, later tasks' descriptions may become partially or fully redundant. The executor handled it correctly (checked, found nothing to do in App.tsx, only cleaned useTapGesture.ts), but the overhead was unnecessary.

### Executor overhead for trivial tasks
TSK-22 (gate EffectComposer behind a boolean) was literally a 2-line change: one `const` and one `{condition && ...}` wrap. Spawning a full agent to read CLAUDE.md, state.md, App.tsx, make the edit, run the build, and write a job entry took ~50 seconds and ~23K tokens. The pipeline has no concept of task weight — a 2-line edit gets the same ceremony as a medium-risk raycasting integration.

### todo-run.md grows without bound
Finalized entries from previous sessions (FAST-2026-04-15, FAST-2026-04-15B) are still in todo-run.md alongside the new BAT-1 through BAT-7 entries. The file is now 100+ lines of historical job records. The finalizer is supposed to clear it, but even when it does, there's no archive — the history just disappears. **Suggestion:** move completed entries to a `todo-run-archive.md` or a `runs/` directory rather than deleting them.

## Structural issues to address

### 1. No pipeline mode toggle
The user said "prioritise implementation over speed" and I interpreted that as serial execution. But there's no formal `mode: serial | parallel | auto` parameter. This should be a first-class concept so the orchestrator doesn't have to interpret natural language intent for execution strategy.

### 2. Triage was redundant for pre-classified items
INB-7 and INB-8 were already in inbox.md with full type/priority/subsystem classifications. The orchestrator correctly skipped re-triaging them, but this was an ad-hoc judgment call. The pipeline should define when triage can be skipped (e.g., items with `status: new` that already have all required fields filled).

### 3. Batch-builder runs inline, not as a proper agent
The batch-builder skill loaded its instructions, but the orchestrator (me) executed the analysis inline rather than spawning a dedicated agent. This worked fine but means the batch-builder's output format and quality depends on whoever is orchestrating. It should either be a spawned agent (consistent output) or explicitly documented as an inline step.

### 4. No lightweight executor mode
For tasks like TSK-22 (2-line change) or TSK-14 (near no-op), the full executor protocol is overkill. A "micro-executor" mode that skips the agent spawn and applies changes directly in the orchestrator context would save significant tokens and time. **Criteria for micro-execution:** task is low risk, touches 1 file, description is unambiguous, no verification beyond build check.

### 5. Cross-task description drift
When the planner writes 15 tasks based on current code state, tasks 10–15 in execution order are working against code that's been modified by tasks 1–9. The planner can't predict exact post-modification state. This is inherent to planning-before-execution, but could be mitigated by:
- Having the planner write descriptions in terms of "what to achieve" not "what to change at line X"
- Re-reading the target file's current state as a mandatory first step (executors already do this, but descriptions could be less prescriptive about exact locations)

### 6. No progress reporting to user during execution
Between spawning the first executor and completing the last one, the user sees individual task completions but no aggregate progress. A simple "BAT-2 complete (2/7 batches, 7/15 tasks)" after each batch would help.

## Priority improvements

1. **Make finalization mandatory.** The orchestrator should always run the finalizer after execution completes. No exceptions.
2. **Add a micro-executor path.** Low-risk, single-file, unambiguous tasks should be executable inline without agent spawn overhead.
3. **Add pipeline mode parameter.** `serial`, `parallel`, or `auto` as a first-class concept, not an informal instruction.
4. **Stop using line numbers in task descriptions.** Use function names, variable names, and code patterns instead.
5. **Handle agent permission failures gracefully.** Detect the failure pattern, extract the analysis, and apply changes in the orchestrator context.
6. **Add aggregate progress reporting.** "Batch X/Y complete, N/M tasks done" after each batch.
